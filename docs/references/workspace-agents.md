- 还应点明本项目必须补足的隔离/状态/出口边界及首个验收动作，沿用用户已有授权，不因此新增确认流程。

## 最终产品形态与用户逐项确认

用户新增要求：**“新增一个对于最终产品形态的描述，需要和用户逐一确认。”**

- 每个项目在`docs/product-form.md`写可审阅的最终目标和首版形态，包含用户入口、主要交互、自动/手动行为、可见产物、管理/恢复体验及首版/后置边界。
- 调查后、依赖这些选择的详细设计前，按[产品形态合同](docs/product-form-contract.md)逐项确认；已开工项目补齐，不将已有组件验收当用户产品确认。
- 按项目/产品主题集中确认高层选择；每题附背景和目的，记录稳定ID、状态和用户答复。内部机制不再逐条询问。已明确的要求不重复问，“继续”、沉默或预选不算全部产品选择获准。
- 产品实质变更仅重核受影响项。确认不是新的安装/API许可，已有授权沿用，例行实现选择无需额外审批。

## 完成时的机制说明

用户要求：每个项目完成时附完整机制说明，**主要作为后续改进skill的依据**。在能力目录的 `docs/mechanisms.md` 交付，按[机制说明合同](docs/mechanism-document-contract.md)验收；该文件在项目完整交付时才可标完成，任务进度说明不能冒充完整说明。

- 以“场景→触发→输入与前置条件→判断规则→工具动作→状态/输出→证据→失败与恢复”为主线，解释为什么这样设计、代价和已知限制。
- 明确哪些是skill可调策略，哪些是plugin/MCP/Host必须执行的硬边界；改skill不能绕过权限或把未验证结果提升为事实。
- 逐条对应来源机制、实际代码/接口和已运行证据。列出可改参数、规则间依赖、建议最小验证及尚待验证的改进假设。
- 用稳定机制编号关联后续skill修订。优先解释对Agent行为有影响的决策，代码细节按需链接，避免只列函数清单或宣传功能。
